# 光滑可破坏地形与采矿技术书

## 1. 目标

保留当前小型、彩色、光滑的地表表现，同时加入类似 Minecraft 的探索、挖掘和矿物收集能力。玩家操作的是可编辑的地形数据，但客户端不直接把地形渲染为规则方块。

本方案的核心原则是：

> 体素保存“哪里能挖”和“是什么材料”，平滑网格决定“玩家看到什么”。

本文件是正在实施的提案，不代表所有阶段已经完成。当前代码和 `xtask` 输出仍然是实现事实来源。

## 2. 当前基线

当前核心世界位于 `crates/core/src/world/mod.rs`：

- `World` 使用 `Vec<BlockType>` 保存有限体素世界；
- 程序化世界通过 `World::get` 在缓存未编辑时调用 `TerrainPipeline`；
- `World::set` 已经能够记录编辑位置；
- `gather_block` 已经执行资源掉落并将方块改为空气；
- 服务器已有 `WorldRevision`、`VoxelDelta` 和 `VoxelChunkSnapshot`。

当前客户端地形位于 `crates/client/src/game_scene/state.rs` 与 `setup.rs`：

- `ProceduralTerrainSurface` 根据高度函数查询地表；
- 可见网格和地形碰撞都由高度图生成；
- 客户端目前没有把地下体素生成成可见网格；
- 因此仅修改 `World` 尚不能改变客户端地表外观。

这意味着第一阶段必须先稳定权威修改链路，之后再把客户端地表查询和碰撞切换到可编辑地形数据。

## 3. 目标架构

```text
程序化生成器 ─┐
               ├─ TerrainRead ── 渲染网格
玩家编辑记录 ──┤                 ├─ 碰撞网格
已加载 chunk ──┘                 ├─ 玩家移动
                                 └─ AI / 内容贴地

客户端 MineRequest
        ↓
服务器权威验证
        ↓
lk2_core::world::mine_block
        ↓
World::set + 掉落 + revision
        ↓
VoxelDelta / chunk snapshot
```

所有权：

- `lk2-core`：材料、可挖规则、程序化生成、编辑结果和确定性纯逻辑；
- `lk2-server`：玩家距离、权限、冷却、保护区域、资源发放和广播；
- `lk2-client`：输入、相机射线、局部网格、局部碰撞和挖掘反馈。

服务器和离线模式必须最终调用同一个核心挖掘规则，不在客户端复制成功判定。

## 4. 分阶段路线

### 阶段 A：权威命令与编辑记录

目标：一次挖掘请求能够安全地修改服务器世界并产生版本化体素增量。

内容：

1. 增加 `GameplayCommandKind::MineTarget`；
2. 核心增加 `mine_block` 入口和聚焦测试；
3. 服务器只接受距离权威玩家位置足够近的目标；
4. 成功后复用 `WorldRevision` 与 `VoxelDelta`；
5. 暂时使用玩家脚下方块作为默认目标，不宣称已经完成相机射线。

验收：重复挖掘同一方块第二次失败；空气、越界和不可掉落材料不会产生资源；成功修改能被 `World::get` 观察到。

### 阶段 B：统一地形查询

增加 `TerrainRead` 抽象，查询优先级为：玩家编辑记录、已加载 chunk、程序化生成结果。地表渲染、碰撞、玩家落脚和内容贴地不再分别调用原始高度函数。

### 阶段 C：光滑地表变形

当前第一步已经在离线场景实现：`M` 键通过相机射线选择地表，调用核心 `mine_block`，成功后把编辑投影为连续凹陷，并重建当前可见地表网格和静态碰撞。同一柱体会从地表向下寻找下一个实体材料，因此可以连续挖深。完整的 `TerrainPatch` 局部重建和地下 chunk 网格仍待后续阶段。

### 阶段 D：地下 chunk 与洞穴

`crates/core/src/world/chunk.rs` 已先提供 `16×16×16` chunk 坐标、负坐标 Euclidean 映射、材料数组和 revision 语义。下一步才把现有 `World` 的有限数组迁移到按需加载 chunk；地下表面使用 Marching Cubes 起步，稳定后评估 Dual Contouring。chunk 网格采样必须包含一圈邻居，修改边界时重建相邻 chunk。

### 阶段 E：矿脉与大地图

矿物以相对地表深度和 3D 噪声生成，不使用固定水平矿层。最后再加入 chunk 流式加载、远景高度图 LOD 和只保存修改过 chunk 的持久化。

## 5. 网络契约

请求：

```rust
GameplayCommandKind::MineTarget { target: [i32; 3] }
```

请求中的目标只表示意图，服务器使用自己的玩家位置、世界数据和规则验证它。客户端不能上传“挖掘成功”或掉落结果。

当前阶段的响应继续复用 `GameplayFeedback` 和 `VoxelDelta`。进入 chunk 阶段后，`VoxelDelta` 增加 chunk revision 语义；客户端拒绝旧 revision，避免网络乱序让地形回滚。

## 6. 材料和矿物

材料仍然可以使用 `BlockType`，但渲染不应等同于方块外观。推荐的矿物分层：

- 浅层：煤和普通石料；
- 中层：铜、铁；
- 深层：金和稀有晶体；
- 洞穴、山脉和遗迹：特殊矿脉。

矿脉使用 3D 噪声和连通扩散生成，使玩家发现的是不规则矿体，而不是一张固定高度的彩色方块表。

## 7. 性能与一致性约束

- 不把大世界扩展继续建立在整张三维数组上；
- 修改后只重建受影响 patch/chunk，不重建整张地形；
- 渲染网格和碰撞网格必须来自同一份最终地形采样；
- 客户端预测可以表现挥镐动画，但不能本地确认掉落；
- 服务器状态、`VoxelDelta` 和 chunk snapshot 的 revision 必须单调递增；
- 任何新增的自然规则都不能绕过 `step_world` 的自然模拟边界。

服务器地形存档路径通过可选环境变量 `LK2_TERRAIN_SAVE_PATH` 提供。配置后，服务器启动会校验并恢复编辑；固定帧 revision 变化时写入临时文件并提交，失败时保留备份。未配置时只使用内存快照。

## 8. 当前实现状态

- 阶段 A：基础命令、核心规则和服务器验证已实现；
- 阶段 B：共享地表查询已开始，离线地表编辑已接入；
- 阶段 C：离线浅坑第一版已实现，仍是整块可见地表重建；
- 阶段 D：`World` 已支持显式 materialize/load/unload，服务器按玩家周围 2 个 chunk 半径流式维护；地下网格和旧数组完全迁移未开始；
- 地下网格底座：`crates/core/src/world/voxel_mesh.rs` 已提供无 Bevy 依赖的 Surface Nets 提取器和球形边界测试，尚未接入在线 chunk 渲染；
- 阶段 E：编辑日志、版本化内存快照和地形临时文件提交/备份读取接口已开始，服务器自动恢复和流式加载未开始；
- 当前不运行闭环截图，因为第一批只涉及核心规则和网络命令，不足以证明最终渲染洞穴已经完成。
