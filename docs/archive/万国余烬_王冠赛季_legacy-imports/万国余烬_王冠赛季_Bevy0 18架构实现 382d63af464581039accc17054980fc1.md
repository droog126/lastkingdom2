# 万国余烬：王冠赛季 Bevy 0.18 架构实现

**版本**：V2.0 重构设计版

**适用范围**：Bevy 0.18 工程架构、ECS 拆分、插件系统、调度、数据驱动、网络权威与 MVP 落地路径

**最后更新**：2026-06-17

**文档定位**：本文件是技术实现蓝皮书的 Bevy 0.18 落地版本。蓝皮书定义系统口径，本文件定义如何在 Bevy 0.18 中拆插件、建组件、排系统、走数据流。

---

## 1. 架构目标

本项目不能按“一个大 `main.rs` + 一堆系统函数”推进。它是多人 PVP、肉鸽事件、有限资源、有限地形、装备数值、神器与经营世界并存的项目，必须从第一版就按模块边界组织。

目标：

- 核心战斗和资源逻辑服务端权威。
- 客户端负责输入、镜头、表现、预测、UI 和反馈。
- 玩法系统通过 Bevy 插件拆分，避免互相直接调用。
- 局内数据使用配置表驱动，避免把数值写死在系统里。
- Bevy `FixedUpdate` 承载确定性模拟，`Update` 承载表现和 UI。
- Bevy `Message` 用于跨系统的帧缓冲消息，核心模拟不依赖散乱的函数互调。
- 全局唯一神器、王权火种、资源池和公开赛计分都可审计。

## 2. Cargo 与工程形态

推荐先做单仓库 workspace，拆出 shared/client/server 三层。即使 MVP 先单机跑，也按服务端权威思维写。

```toml
[workspace]
members = [
  "crates/ember_shared",
  "crates/ember_game",
  "crates/ember_client",
  "crates/ember_server",
]

[workspace.dependencies]
bevy = "0.18.1"
serde = {version = "1",features = ["derive"] }
ron = "0.8"
uuid = {version = "1",features = ["serde", "v4"] }
```

| crate | 职责 | 是否依赖渲染 |
| --- | --- | --- |
| `ember_shared` | ID、配置结构、消息结构、通用枚举、数值公式纯函数 | 否 |
| `ember_game` | Bevy ECS 玩法插件：资源、装备、战斗、地形、神器、国家 | 不直接依赖窗口，可被 client/server 使用 |
| `ember_client` | 客户端 App、渲染、输入、UI、音效、VFX、相机 | 是 |
| `ember_server` | Headless/专服 App、权威模拟、快照、审计、排行榜提交 | 否 |

MVP 可以先只有 `ember_game` + `ember_client`，但代码边界仍按上述形态放。

```rust
fn main() {
    App::new()
        .add_plugins(DefaultPlugins)
        .add_plugins(EmberGamePlugin::client())
        .run();
```

```rust
use bevy::prelude::*;
use ember_game::EmberGamePlugin;

fn main() {
    App::new()
        .add_plugins(MinimalPlugins)
        .add_plugins(EmberGamePlugin::server())
```

`EmberGamePlugin` 不应该知道窗口、键鼠、UI 皮肤；它只注册玩法状态、资源、消息、组件和系统。客户端和服务端通过不同 feature 或构造函数注册不同表现层。

## 6. State 设计

Bevy 的 `State` 适合客户端大流程，不适合服务端同时跑多场对局。推荐：

- 客户端使用 Bevy `State` 管 UI 和场景切换。
- 单局阶段在 MVP 单场模式下可以用 Bevy `State`。
- 专服多房间时，对局阶段应变成 `MatchPhase` 组件/资源，不能用全局 App State 表示每个房间。

```rust
#[derive(Debug, Clone, Copy, Default, Eq, PartialEq, Hash, States)]
pub enum AppState {
    #[default]
    Boot,
    Loading,
    MainMenu,
    InMatch,
    CrownWorld,
}

#[derive(Debug, Clone, Copy, Default, Eq, PartialEq, Hash, States)]
pub enum MatchState {
    #[default]
    OpeningProtection,
    WildRace,
    SovereignRise,
    Endgame,
    Finished,
}
```

客户端注册方式：

```rust
app
    .init_state::<AppState>()
    .init_state::<MatchState>()
    .add_systems(OnEnter(AppState::Loading), load_game_configs)
    .add_systems(OnEnter(AppState::InMatch), spawn_match_scene)
    .add_systems(OnExit(AppState::InMatch), cleanup_match_scene)
    .add_systems(Update, update_match_ui.run_if(in_state(AppState::InMatch)));
```

## 7. Schedule 与 SystemSet

推荐固定模拟帧率 30Hz。表现层可以跟随显示帧率。

```rust
#[derive(SystemSet, Debug, Clone, PartialEq, Eq, Hash)]
pub enum SimSet {
    ReceiveNet,
    ReadInput,
    BuildIntent,
    ValidateRules,
    Movement,
    Interaction,
    Combat,
    ResourceAndLoot,
    EquipmentAndStats,
    NationAndArtifact,
    ScoreAndAudit,
    Snapshot,
}
```

注册顺序：

```rust
app
    .insert_resource(Time::<Fixed>::from_seconds(1.0 / 30.0))
    .configure_sets(
        FixedUpdate,
        (
            SimSet::ReceiveNet,
            SimSet::ReadInput,
            SimSet::BuildIntent,
            SimSet::ValidateRules,
            SimSet::Movement,
            SimSet::Interaction,
            SimSet::Combat,
            SimSet::ResourceAndLoot,
            SimSet::EquipmentAndStats,
            SimSet::NationAndArtifact,
            SimSet::ScoreAndAudit,
            SimSet::Snapshot,
        )
            .chain()
            .run_if(in_state(AppState::InMatch)),
    );
```

调度原则：

| Schedule | 用途 |
| --- | --- |
| `Startup` | 初始化日志、配置默认值、注册资源 |
| `OnEnter` / `OnExit` | 场景和 UI 生命周期 |
| `PreUpdate` | 客户端输入采样、网络包接收、外部消息转意图 |
| `FixedUpdate` | 权威模拟：移动、战斗、资源、神器、计分 |
| `Update` | 镜头、UI、动画状态机、客户端预测显示 |
| `PostUpdate` | VFX、音效、名称板、小地图、Transform 同步后的表现 |

## 8. Message 与 Observer 使用

Bevy 0.18 中，跨系统帧缓冲通信使用 `Message`。本项目核心模拟优先使用 `Message`，少用立即触发的 Observer，避免时序难追。

```rust
#[derive(Message, Debug, Clone)]
pub struct DamageIntentMsg {
    pub attacker: Entity,
    pub target: Entity,
    pub ability_id: AbilityId,
}

#[derive(Message, Debug, Clone)]
pub struct DamageAppliedMsg {
    pub source: Entity,
    pub target: Entity,
    pub amount: i32,
    pub damage_type: DamageType,
}

pub struct CombatPlugin;

impl Plugin for CombatPlugin {
    fn build(&self, app: &mut App) {
        app
            .add_message::<DamageIntentMsg>()
            .add_message::<DamageAppliedMsg>()
            .add_systems(
                FixedUpdate,
                (
                    collect_damage_intents.in_set(SimSet::Combat),
                    resolve_damage_intents.in_set(SimSet::Combat),
                    apply_damage_results.in_set(SimSet::Combat),
                )
                    .chain()
                    .run_if(in_state(AppState::InMatch)),
            );
    }
}
```

使用约定：

| 类型 | 用途 |
| --- | --- |
| `Message` | 战斗、掉落、开箱、装备变化、资源变化、计分、神器激活 |
| `Event` / Observer | 本地表现、一次性 UI/VFX 反馈、实体生命周期小回调 |
| `Resource` | 配置、全局资源池、对局时钟、规则状态 |
| `Component` | 实体状态、玩家、装备、怪物、POI、容器、神器 |

## 12.1 30Hz 权威模拟与高帧渲染

服务端权威模拟推荐 30Hz，不代表画面只能 30 帧，也不代表输入只能 30 次/秒。正确拆法是：

- `FixedUpdate`：固定 30Hz，只跑权威逻辑，处理移动、碰撞、战斗、采集、矿坑、资源、地形、神器。
- `PreUpdate`：按渲染帧率采样本地输入和鼠标视角，积累到输入缓冲。
- `Update` / `PostUpdate`：按显示帧率跑相机、动画、VFX、UI 和插值后的可视 Transform。
- 网络快照：服务端按 30Hz 或更低的聚合频率发权威快照，客户端对远端实体使用插值缓冲。

核心原则：**权威 Transform 和可视 Transform 分离**。

```rust
#[derive(Component, Clone, Copy)]
pub struct SimTransform {
    pub previous: Transform,
    pub current: Transform,
    pub tick: u64,
}

#[derive(Component)]
pub struct RenderProxy {
    pub visual_entity: Entity,
}

#[derive(Component)]
pub struct SnapshotBuffer {
    pub frames: VecDeque<RemoteSnapshotFrame>,
    pub interpolation_delay_ticks: u8,
}
```

本地玩家流程：

```
PreUpdate:
  sample mouse/camera/input every render frame
  accumulate into InputAccumulator

FixedUpdate 30Hz:
  consume accumulated input for this tick
  SimTransform.previous = SimTransform.current
  integrate movement/combat/collision into SimTransform.current
  emit confirmed state and prediction markers

Update/PostUpdate uncapped:
  alpha = fixed_overstep / fixed_timestep
  visual_transform = lerp(previous, current, alpha)
  camera follows visual_transform plus local look input
  animation blends using render delta
```

远端玩家流程：

```
Receive Snapshot:
  push ticked remote transform into SnapshotBuffer

Render Frame:
  render_time = estimated_server_tick - 2 or 3 ticks
  find two snapshots around render_time
  interpolate position/rotation
  if missing, extrapolate for at most 3 ticks
  after that, hold or fade correction rather than rubber-band hard snap
```

推荐延迟：

| 对象 | 插值延迟 | 原因 |
| --- | --- | --- |
| 本地玩家 | 0 tick，预测 + 服务端纠偏 | 保证手感 |
| 队友/敌人 | 2-3 ticks | 平滑网络抖动，约 66-100ms |
| 怪物/资源/地形 | 2-4 ticks | 可读优先，不需要极低延迟 |
| 火种/神器 | 1-2 ticks + 事件强提示 | 战略目标要更及时 |

纠偏规则：

- 小误差：0.1-0.3m 内，数帧平滑拉回。
- 中误差：0.3-1.0m，0.1s 内加速修正。
- 大误差：超过 1.0m 或穿墙，直接权威 snap，并播放失衡/校正表现。
- 战斗命中、拾取火种、神器激活、地形改造以服务端结果为准，不做客户端最终确认。

输入规则：

- 鼠标视角和相机旋转按渲染帧率响应。
- 移动意图按固定 tick 打包发送，带 input sequence。
- 攻击、招架、施法、交互按按钮边沿记录时间戳，再映射到最近服务端 tick。
- 完美招架、闪避无敌、命中有效帧必须至少覆盖多个 tick，不能设计成只容许 1 tick 的超窄窗口。

相机规则：

- 水平/垂直视角可以在 `Update` 即时转动，不等待 30Hz。
- 角色位移跟随插值后的可视 Transform。
- 第一人称手臂和第三人称模型都读可视层，不直接读权威 Transform。
- 受击反馈、剑轨和法术 VFX 使用权威事件触发，但播放过程按渲染帧率。

这套方案会让服务端保持稳定、可审计，同时客户端在高刷屏上仍然顺滑。

## 13. 网络架构

多人 PVP 推荐服务端权威。

客户端发送：

- 输入轴：移动、视角、疾跑、闪避。
- 意图：攻击、招架、施法、采集、开箱、拾取、丢弃、装备、建造、激活神器。
- UI 操作：队伍、国家、地图标点。

服务端验证：

- 保护期和 PVP 规则。
- 距离、视线、负重、耐力、MP、材料。
- 宝箱开启条件。
- 装备槽和耐久。
- 神器持有者、冷却、封印地点。
- 地形改造预算和关键路径。

服务端广播：

- 快照：位置、生命、装备可见状态、怪物状态、资源节点和矿坑槽位状态。
- 战略事件：火种掉落、神器现世、神器激活、王座进度、国家灭亡。
- 审计事件：资源池变化、公开赛计分。

本项目不应让客户端直接改生命、资源、装备、神器状态。客户端最多做预测和表现，服务端快照覆盖权威结果。

## 14. 有限地形实现

不要把世界做成完全自由体素沙盒。推荐“静态地形 + 可编辑覆盖层”。

| 层 | 内容 | Bevy 实体 |
| --- | --- | --- |
| Base Terrain | 初始地图 mesh、碰撞、导航 | `TerrainChunk` |
| Edit Overlay | 沟、墙、桥、道路、符文槽、阵眼 | `TerrainEditEntity` |
| Protected Paths | 王座、遗迹、Boss、出生区关键路径 | `ProtectedPath` |
| Budget | 玩家/国家改造预算 | `TerrainEditBudget` |

系统流程：

1. 玩家发起 `TerrainEditIntentMsg`。
2. 服务端校验材料、预算、尺寸、关键路径。
3. 生成 `TerrainEditEntity`，扣资源。
4. 更新碰撞、导航和小地图。
5. 写审计日志。

## 15. 装备与数值实现

装备改变组件，不直接改玩家字段。所有最终数值由 `StatPlugin` 聚合。

```
EquipmentInstance + Loadout + StatusEffect + CarryState + ArtifactBurden
  -> StatRecalculateRequest
  -> StatBlock
  -> Movement / Combat / Arcana 读取 StatBlock
```

规则：

- 穿脱装备只发消息，不让 UI 系统直接改数值。
- 耐久变化只改装备实例，再触发数值重算。
- 神器负担进入 `ArtifactBurden`，不是永久写入装备。
- 经营皮肤没有 `StatModifier`。

## 16. 神器实现

神器作为实体存在，不是普通 item。

```rust
#[derive(Component)]
pub struct UniqueArtifact {
    pub artifact_id: ArtifactId,
    pub state: ArtifactState,
    pub cooldown_until_tick: u64,
    pub active_until_tick: Option<u64>,
    pub controlling_nation: Option<NationId>,
}

#[derive(Component)]
pub struct ArtifactCarrier {
    pub player: Entity,
}
```

神器流程：

```
Manifested -> Carried -> Active -> Carried
Carried -> Dropped -> Carried
Carried -> Sealing -> Sealed
Sealing -> Dropped
Dropped -> Recalled -> Manifested
```

神器系统拆分：

| 系统 | Schedule | 作用 |
| --- | --- | --- |
| `manifest_artifacts` | FixedUpdate / NationAndArtifact | 根据事件生成神器 |
| `pickup_artifact` | FixedUpdate / Interaction | 校验拾取、负重、单人上限 |
| `activate_artifact` | FixedUpdate / NationAndArtifact | 扣材料、套用主动能力 |
| `tick_artifact_burdens` | FixedUpdate / NationAndArtifact | 暴露、消耗、诅咒 |
| `counter_artifact_effects` | FixedUpdate / Combat | 处理打断和反制 |
| `start_artifact_seal` | FixedUpdate / NationAndArtifact | 开始封印读条 |
| `resolve_artifact_seal` | FixedUpdate / NationAndArtifact | 成功或打断 |
| `broadcast_artifact_reveal` | PostUpdate / 表现层 | 小地图和 VFX 提示 |

## 23. Message 命名与方向

命名要区分“玩家请求”和“权威结果”。

| 后缀 | 含义 | 示例 |
| --- | --- | --- |
| `IntentMsg` | 客户端或本地输入提出的意图，必须校验 | `AttackIntentMsg`, `OpenContainerIntentMsg` |
| `RequestMsg` | 系统内部请求，可能失败 | `StatRecalculateRequestMsg` |
| `CommittedMsg` | 服务端已经确认的世界变化 | `TerrainEditCommittedMsg` |
| `AppliedMsg` | 结算已应用 | `DamageAppliedMsg` |
| `ChangedMsg` | 状态从旧值变新值 | `PoiStateChangedMsg`, `DurabilityChangedMsg` |
| `GrantedMsg` | 奖励或资源已发放 | `LootGrantedMsg` |

红线：

- UI 只能发 `IntentMsg`，不能发 `AppliedMsg`。
- 客户端预测只能改表现层缓存，不能改服务端权威组件。
- `ResourceDeltaMsg` 必须带 reason、source_entity、audit_id。
- 神器、王权火种、资源池、公开赛计分的结果消息必须由服务端系统产生。
