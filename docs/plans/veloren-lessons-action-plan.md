# Veloren 经验落地方案

> 本文是实施前方案，不代表当前代码已经完成这些目标。实现时以当前代码、`xtask` 输出和工程基线为准；若方案与实现冲突，先记录冲突并重新评估方案。

## 1. 目标

把从 Veloren 学到的自然模拟、世界流式、网络同步、客户端缓存和工程治理经验逐步落到 `lastkingdom2`：

- 高层自然模拟与客户端细节解耦；
- 区域化、可变频率的远景模拟；
- 简单、可迁移、可恢复的模拟数据；
- 由事件和可组合规则形成可验证的复杂行为。
- chunk 加载、邻居边界、网络请求预算和客户端容错；
- 资源、资产、内容数据和测试的长期工程边界。

本方案不包含大规模世界重写、完整 NPC 社会模拟、网络协议重做或视觉重做。

## 2. 不可改变的架构边界

1. `lk2_core::simulation::step_world` 继续是自然世界唯一模拟入口。
2. 规则只在 core 模拟层改变状态；server 不复制生态规则。
3. server 继续采用 `authority -> replication / observation / persistence` 投影链。
4. 区域 LOD 只调整模拟频率和工作预算，不改变规则语义。
5. PNG 只证明表现；模拟正确性以测试、状态工件和机器断言为准。

## 3. 差距定义与取舍

`lastkingdom2` 当前约有 4.7 万行 Rust，Veloren workspace 约有 37.5 万行 Rust。这个差距主要来自产品范围，不应作为直接追赶的代码目标。

### 当前必须补齐的工程能力

| 能力 | 当前问题 | 计划目标 |
| --- | --- | --- |
| 自然模拟 | 规则仍以直接步骤为主 | 事件边界、可组合规则、确定性快照 |
| 区域调度 | 已有 LOD，但仍需完整 elapsed/catch-up 语义 | 有界补算、预算和多玩家合并 |
| 持久化 | 已有 DTO 和保存路径 | 迁移、损坏恢复、完整区域恢复 |
| chunk 世界 | 正在建设加载/卸载和 mesh | revision、邻居边界、重新进入一致性 |
| 网络同步 | 有 authority/projection 骨架 | 兴趣管理、请求预算、过期消息处理 |
| 客户端生命周期 | 表现层和资源正在快速增长 | 缓存、实体、mesh、材质的明确淘汰边界 |
| 内容与资产 | manifest 和生成工具正在形成 | 可检查、可缓存、可复现的数据管线 |
| 验证 | 已有 tests、health 和 assertions | 分层集成测试及性能基准 |

### 暂不追赶的 Veloren 范围

以下能力保留为长期方向，不进入本轮实施承诺：

- 数万 NPC 的完整社会、经济、派系和贸易模拟；
- 完整 MMO 级聊天、权限、账号和服务器运维系统；
- 多协议网络栈和极大规模并发玩家优化；
- 全量物品、职业、技能、任务和本地化内容迁移；
- 为了规模而引入复杂插件生态或大范围 workspace 重构。

取舍原则是：先补齐会影响当前自然世界正确性、服务器稳定性和资产生命周期的能力；只有真实玩法需求和性能证据出现后，才扩展长期能力。

## 4. 分阶段实施

### 阶段 A：基线与接口冻结

先不增加玩法，完成以下只读盘点：

- 记录当前 `step_world`、区域调度、server authority 和存档 DTO 的调用链；
- 建立规则迁移表：`keep / adapt / move / retire`；
- 补齐现有行为的聚焦测试和当前健康证据；
- 冻结事件、快照和规则接口，避免后续各 crate 自行扩展。

验收：可以从测试和 `xtask` 工件说明一条完整的权威自然链路。

### 阶段 B：事件驱动规则层

在 core 内定义最小事件边界，例如资源变化、植物状态变化、动物出生、动物死亡和迁徙。

- 事件只表达模拟事实，不携带 Bevy entity 或渲染对象；
- 规则接收事件并产生有限、可审计的状态变更；
- 保留一个统一的 `step_world` 编排器；
- 先适配已有生态规则，再新增行为；
- 每条规则支持单独测试，必要时可关闭。

验收：相同输入和 tick 产生相同快照；禁用一条规则不会破坏其他规则的基本运行。

### 阶段 C：区域调度与远景模拟

完善 `Active / Nearby / Distant` 的调度语义：

- 显式传递 elapsed time，而不是假设每次调用都是一个固定 tick；
- 保留未完成的时间余量；
- catch-up 设上限，并把剩余工作留到后续 tick；
- 多玩家请求同一区域时取最高频率需求；
- 为每个区域限制单 tick 的计算预算。

验收：区域切换 LOD 不丢时间；远区不会因重新靠近而产生无界补算；多玩家移动顺序不影响最终 LOD。

### 阶段 D：扁平状态与存档迁移

将可长期保存的自然状态整理为版本化 DTO：

- 区域身份、快照、资源池、LOD、恢复 tick 和 schema version；
- 对旧版本提供显式迁移函数；
- 缺失实体、失效关系、未知字段和部分损坏数据采用防御式恢复；
- 区域卸载后保留可恢复记录，重入时恢复而不是重新生成；
- 不把临时 Bevy entity、渲染句柄和网络连接状态写入自然存档。

验收：当前版本可保存/加载；旧版本 fixture 可迁移；失效关系不会导致整个世界加载失败。

### 阶段 E：规则组合与服务器投影

- 将生态、资源、动物关系拆成独立规则模块；
- 明确规则执行顺序和冲突处理；
- 将事件/快照分别投影到 replication、observation 和 persistence；
- 验证区域卸载、恢复、复制和观测使用同一份权威结果；
- 不在 projection 层引入新自然规则。

验收：server 集成测试能够证明四条投影都来自同一个 authority 报告。

### 阶段 F：自动化证据与性能复盘

- 增加事件、LOD、catch-up、迁移和关系失效的 focused tests；
- 扩展 `xtask` 状态工件和机器断言；
- 记录区域 tick、规则事件计数、catch-up 剩余量和存档恢复结果；
- 最后测量远景模拟 CPU 成本、单 tick 峰值和存档大小；
- 性能结果只作为评估数据，不写成未经验证的固定承诺。

验收：健康工件能够区分“模拟成功”“投影成功”“存档成功”和“表现成功”。

### 阶段 G：chunk、邻居和地形流式

这部分只处理世界数据与表现数据的边界，不把客户端缓存变成新的世界权威：

- 明确 chunk 的加载、保留、卸载和恢复状态；
- 为 meshing 保留必要邻居和边界缓冲；
- 对修改过的 chunk 保留 revision，支持重新加载后的连续性；
- 区分生成 chunk、持久化 chunk 和客户端缓存 chunk；
- 为地形快照/增量更新定义失败、过期和丢失时的降级路径。

验收：移动、卸载、重新进入和相邻 chunk 更新不会造成地形裂缝、旧 revision 覆盖新状态或客户端永久等待。

### 阶段 H：网络兴趣管理与客户端容错

- 按玩家位置和视距合并 chunk 请求；
- 限制每 tick 的请求数、pending 数和重试次数；
- 处理超时、乱序、重复和过期消息；
- 将网络快照、客户端缓存和渲染实体分开管理；
- 对远区采用更低精度或更低频率的同步策略。

验收：单个玩家快速移动、多玩家重叠视距和服务端延迟时，客户端不会产生无界请求、永久 pending 或旧状态回滚。

### 阶段 I：资产、内容和工程治理

- 统一资产 manifest、缓存、路径覆盖和重复资产检测；
- 将仍会增长的规则、配方和内容参数保持在数据层；
- 为资产解析、内容导出和模型预算建立独立检查；
- 为 core、server、client、网络和资产加载分别保留窄测试入口；
- 必要时增加 profiling/release 配置，但不把构建 profile 逻辑散落到脚本中。

验收：缺失或重复资产能在启动/检查阶段给出明确错误；内容变更不需要修改无关的模拟代码；各层可单独验证。

## 5. 验证策略

每个阶段完成一个完整批次后再验证：

- core 规则：`cargo test -p lk2_core` 或更窄的测试目标；
- server 接线：`cargo test -p lk2_server` 或 authority 聚焦测试；
- 文档变更：`just audit-docs`；
- 仅技能契约变更：`just audit-skills`；
- 只有验收明确要求真实运行时证据时，才运行闭环和截图。

## 6. 风险与停止条件

- 如果事件层导致 `step_world` 出现第二套规则入口，立即停止迁移并回退设计；
- 如果 LOD 只改变更新次数却没有 elapsed 语义，不能宣称支持远景模拟；
- 如果存档只能保存快照而不能恢复调度和资源状态，不能进入下一阶段；
- 如果 projection 测试无法证明来源唯一，不能扩展客户端表现；
- 如果性能问题来自重复生成资源，应转入资源生命周期专项排查，而不是继续调大预算。

## 7. 代码量与工期估算

以下是首次完整落地的工程量级估算，单位为“新增或实质改动的 Rust/Python/配置行数”，不包含格式化变化、生成资产二进制和已有 dirty worktree 改动。实际数字以阶段 A 的盘点为准。

| 范围 | 生产代码 | 测试/断言 | 预计结果 |
| --- | ---: | ---: | --- |
| A：基线与接口冻结 | 100–300 | 200–500 | 迁移账本、接口草案、基线测试 |
| B：事件驱动规则层 | 400–900 | 500–1,000 | 事件、规则调度、快照事件记录 |
| C：区域调度与 catch-up | 250–600 | 400–800 | LOD、elapsed、预算和补算控制 |
| D：状态与存档迁移 | 400–900 | 500–1,000 | DTO、schema migration、损坏恢复 |
| E：规则组合与 server 投影 | 300–700 | 500–900 | 规则模块化和四路投影验证 |
| F：xtask 工件与性能证据 | 300–700 | 300–700 | 健康字段、断言、性能采样 |
| G：chunk 与邻居边界 | 700–1,500 | 700–1,400 | 流式加载、revision、邻居安全 |
| H：网络兴趣与客户端容错 | 600–1,400 | 700–1,500 | 请求预算、超时、过期消息处理 |
| I：资产、内容和工程治理 | 300–800 | 400–900 | manifest、检查器、分层测试入口 |
| **合计** | **3,350–7,800** | **4,200–8,700** | **约 7,500–16,500 行变更** |

估算不等于一次性重写目标。建议先实现 A–F，约 **2,050–4,800 行生产代码**；G–I 只有在 chunk、网络或资产问题成为实际瓶颈时再实施，约 **1,300–3,000 行生产代码**。

## 8. 实施顺序与里程碑

推荐顺序为：

```text
A 基线
  -> B 事件规则
  -> C 区域调度
  -> D 存档迁移
  -> E server 投影
  -> F 自动化证据
  -> G chunk 边界
  -> H 网络容错
  -> I 资产与工程治理
```

每个阶段必须满足本阶段验收条件，并完成最窄验证后才能进入下一阶段。任何阶段发现新的第二权威入口、无法恢复的存档语义或无界资源增长，都应暂停扩展并先修复架构边界。

## 9. 首个实现批次

首批只做阶段 A 和阶段 B 的最小切片：

1. 冻结现有生态规则清单和事件接口；
2. 选择一个资源变化事件和一个动物生命周期事件；
3. 保持旧行为不变，将它们接入统一事件记录；
4. 增加确定性测试和 server 投影测试；
5. 评审结果后再决定是否扩展到迁徙、关系失效和存档迁移。

## 10. 实施记录

以下记录区分已有代码/测试证据与本批次新增、尚待包级验证的切片，不把尚未完成的阶段提前标为完成：

- 阶段 A/B：`step_world`、`NatureEvent`、确定性快照和 server 四路投影已经形成统一入口；相关测试覆盖相同输入、tick 和投影来源唯一性。
- 阶段 C：区域 `Active / Nearby / Distant`、显式 elapsed、有限 catch-up 和多请求取最高频率已有 core/server 聚焦测试。
- 阶段 D（区域存档切片）：区域快照、资源池、LOD、恢复 tick 和 schema 已进入 DTO；本批次补充了 schema `0 -> 1` 的显式迁移、逐条坏记录跳过和主文件损坏时的备份回退测试，包级测试仍待工作树清理后验证。
- 阶段 E：server 的 replication、observation、persistence 都从同一份 authority report 投影，projection-only 插件不会启动第二套自然模拟。
- 阶段 F（xtask 证据切片）：自然观测支持可选的事件计数、区域 tick、catch-up 余量和存档恢复标记；server capture 已写入主区域证据，健康扩展会保留这些字段，并在字段存在时检查区域 tick 不超前、事件计数不小于观测事件数。
- 阶段 G（revision/邻居边界切片）：客户端切换 chunk 或从 revision gap 等待全量快照后，会以新快照 revision 重置 delta cursor，避免旧 cursor 造成永久 pending；server fixture 验证 border snapshot 携带相邻 chunk 的修改，core fixture 验证卸载重入后编辑内容和 chunk-local revision 保持连续。
- 阶段 H（网络容错第一切片，待包级验证）：新增可靠 `TerrainSnapshotRequest` 协议；客户端检测 revision gap 后按单 pending、冷却窗口和最多三次重试发送 resync 请求，耗尽窗口后进入有限退避而不是永久 pending，收到 full snapshot 后清除等待/退避并重置预算；server 按连接合并请求、施加 15 tick 冷却，并仅对受控玩家当前兴趣 chunk 强制重新投影完整 snapshot。新增 client budget、协议 round-trip 和 server budget 聚焦测试；尚未宣称包级编译通过。

下一步是在并行构建资源释放后补跑 client/server 包级验证，并根据结果补充服务端无响应或连接断开时的可观测降级状态；在此之前不宣称自然世界已经具备完整的闭环健康证据。
